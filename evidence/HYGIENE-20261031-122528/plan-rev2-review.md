## 1) มติ (ฌ) ถูกนำมาใช้แค่ครึ่งเดียว

**มติ (ฌ)** (`NPC-1-ACT-1` น. 274) มีสองส่วน:
1. ข้อความรางวัลบนจอแสดง **สองหน่วย** เช่น "1 ชั่วยาม (5 วันงาน)"
2. **ข้อความ "คาดว่าแต่ละวัน…" ของเกมคงตรงเดิม**

**ในแผน:** บรรทัด 22 และ 29 รับส่วนที่ 1 ครบ แต่ **ไม่ปรากฏส่วนที่ 2 เลย** · ตรงกันข้าม บรรทัด 41 (A1.5-5) สั่งให้หา "จุด format ข้อความ 'คาดว่าแต่ละวัน…'/ป้าย 'N วัน'" ซึ่งอ่านได้สองทาง — ถ้าตีความว่า mod จะ **แก้** ข้อความนั้น จะขัดมติ (ฌ) ทันที

**ผลของ a15:** จุด format อยู่ที่ `AreaController$$FreshAreaBuildingButton` (`String.Format` + Concat + `LTLocalization$$SetText` ×3) [DISASM] แต่ **template มาจาก data asset** (`describe`/`text` ใน `AreaBuildingChoice`) — ค่าจริง = UNKNOWN (A1.5-2)

**ข้อเสนอแก้ (เพิ่มบรรทัดใน §2 ข้อ 3 + §1):** ระบุชัดว่า
- mod **ไม่แก้** ข้อความ/ตัวเลขดิบของเกม (ตาม ฌ ครึ่งหลัง) — ถ้าจำเป็นต้องสื่อสารกับผู้เล่น ให้ **เพิ่มบรรทัดของ mod เอง** (overlay/ป้ายแยก) ที่ไม่ทับ node เดิม
- A1.5-5 ใน §6 เปลี่ยนถ้อยคำจาก "จุด format ข้อความ…" เป็น "ยืนยันว่า**ไม่ต้อง**แตะข้อความเกม + ระบุ node ที่ mod จะเพิ่มของตัวเอง"

## 2) รายการ "ตัวขับวันเดิม" ยังเปิด (`ฯลฯ`) — ขัดหลักของทาง (ii)

**R6-2** (น. 296) ระบุตัวขับวันเดิม: `WorkingUIController.Update`, `BigMapController.FixedUpdate`, `FinishExploreMap`, plot `*Result`, **`ฯลฯ`** ⇒ ต้อง gate หรือแปลง
**แผนบรรทัด 28** คัดลอกมาทั้งวลีรวม `ฯลฯ` · **บรรทัด 31** ยังบอก "รายละเอียดการแปลงรายสาย = ออกแบบใน A2" · **บรรทัด 65** ย้ำว่า "รายละเอียด gate/แปลงรายสาย = ออกแบบใน A2"

**ปัญหาเชิงกลไก:** ทาง (ii) = "นาฬิกา host เป็น driver เดียว" — ถ้ารายการตัวขับ **ไม่ปิด** จะ **ตรวจสอบความครบไม่ได้** และ double-drive ที่หลุดจะทำให้ปฏิทินเดินเร็วขึ้นแบบเงียบ ๆ (อาการที่ผู้เล่นเห็นเป็น "วันกระโดด" ไม่ใช่ crash) — เป็นความเสี่ยงชนิดที่ **ตรวจไม่เจอด้วยการเล่นปกติ**

**ข้อเสนอแก้:** เพิ่ม exit criteria ของ A2 (หรือ A1.6 สั้น ๆ) ว่า
- ต้องมี **inventory ปิด** ของทุก call site ที่เรียก `ChangeDay`/`ChangeHour`/leaf ที่เดินวัน (static sweep จาก `dump.cs` + disasm ของ caller) พร้อมตาราง `method → gate | convert | คงเดิม(พร้อมเหตุผล)`
- เกณฑ์ผ่าน = **ไม่มีแถว "ฯลฯ"/"รอเก็บเพิ่ม"** ในตาราง · ถ้ายังเหลือ = หยุดรายงาน (ห้ามเข้า A3)
- บันทึกตารางลง evidence ของ stage (เช่น `day-driver-inventory.md`)

*(ผล A1.5-4 ปิดความเสี่ยงของ `PartyController` ไปแล้ว — ไม่เดินปฏิทิน — แต่ยังเหลือสายอื่นที่ยังไม่มีใครไล่ครบ)*

## 6) **[สูง]** A2 ยังไม่มีนิยามของสิ่งที่ต้องตัดสินก่อนเขียนโค้ด

**แผนบรรทัด 42** (A2) ระบุแค่ "pure logic + เทสต์ offline (สูตร (ฉ) · ช-A ตามผล A1.5-1 · กันจ่ายซ้ำ · กฎ α + (ii)) + compile-only build" และ exit = "เทสต์เขียวครบ · build 0W/0E · provenance READY"

ยังขาดนิยามที่ทำให้ "เทสต์เขียว" มีความหมาย:

| # | เรื่องที่ยังไม่นิยาม | ทำไมสำคัญ (เชิงตัวเลข) |
|---|---|---|
| a | **"วันงานที่ครบ" (D2) นับที่วินาทีไหน** | เวลาต่อ N วัน = `max(30, 12N)` ⇒ วินาทีต่อวันงาน **ไม่คงที่**: N=1 → 30 s/วัน · N=5 → 12 s/วัน · N=10 → 12 s/วัน · N=15 → 12 s/วัน · N=20 → 12 s/วัน · N=2 → 15 s/วัน. ถ้าไม่นิยามขอบ (floor vs ปัดขึ้น, นับที่ elapsed ≥ k×unit) จะได้จำนวนวันงานต่างกัน ±1 ที่ขอบ ⇒ **รางวัลต่างกัน 1 วันงาน** ทุกครั้งที่ยกเลิก |
| b | **การฉีดนาฬิกา** | pure logic ต้องรับ "เวลาปัจจุบัน" เป็นพารามิเตอร์/interface ไม่ใช่ `Time.time`/`DateTime.Now` — ไม่งั้นเทสต์ offline ต้อง sleep จริง (180 s ที่ N=15) ซึ่งจะทำให้ suite ช้าและ flaky |
| c | **ค่าคงที่ vs config** | มติ (ช) ตัด `rewardDaysPerShichen` ออกแล้ว — แต่ **สูตร `max(30,12N)` เอง** จะ hardcode หรือ config? ถ้า config ต้องระบุที่เก็บ (บทเรียน RUNTIME: MelonPreferences ทำ dotted pref พัง ⇒ ต้องเป็นไฟล์ flat แบบ `net.cfg`) |
| d | **ขอบเขต pure logic** | ไฟล์/เนมสเปซใดบ้างที่ห้ามอ้าง Unity/IL2CPP เพื่อให้เทสต์รันนอกเกมได้ · ต้องมี static check กันหลุด (มี `tools/s2_static_check.py` เป็นแบบอย่าง) |
| e | **วิธีวัด "0 day-skip" ของ A3** | exit criteria (น. 43) เขียน "ปฏิทินเดินจริงระหว่าง task (**0 day-skip**)" แต่ไม่ได้บอกว่า**วัดอย่างไร** — จากประสบการณ์ S1.5/S2 ต้องระบุคีย์: `ChangeDay` ถูกเรียก count = 0 ระหว่าง task? หรืออ่าน `timeLabel`/วันที่ก่อน-หลัง? **ข้อเสนอแก้:** เพิ่ม **§2.5 "นิยามที่ A2 ต้องปิดก่อนเขียนโค้ด"** 5 ข้อ (a–e) พร้อมเกณฑ์ผ่านเป็นข้อ ๆ — และให้ A2 exit criteria อ้างถึงนิยามเหล่านี้ ("เทสต์ครอบ a–d ครบ · e เป็นเกณฑ์ของ A3")

## 7) ไม่มีชื่อ pref kill-switch + รายการ hook ที่ R6-4 อ้างถึงยังไม่เป็นตารางปิด

**ก) kill-switch:** แผนบรรทัด 48 (Rollback) เขียน "pref/switch ปิดพฤติกรรมใหม่ (mod นิ่งเมื่อ pref false — fail-closed)" — **ไม่มีชื่อ key ไม่มีที่เก็บ ไม่มีค่า default**
บทเรียน RUNTIME ที่ต้องใช้: MelonPreferences ทำ dotted pref (`coop.net.enabled`) พังสองทาง (TOML เสียทั้งไฟล์ + ML เขียนกลับเป็นตารางซ้อนแล้วทิ้ง key) ⇒ ทางแก้ที่ใช้ได้จริงคือ **ไฟล์ flat แยกที่ ML ไม่แตะ** (`UserData\LongYinCoop\net.cfg` เป็นแบบอย่าง)

**ข้อเสนอแก้:** ระบุชื่อจริง เช่น `UserData\LongYinCoop\act1.cfg` · key `enabled` (default **false** = fail-closed) · รูปแบบ `key = value` ธรรมดา · **ปฏิเสธ `[section]`** เหมือน `S2NetConfig` · และระบุว่าถ้าไฟล์หาย/อ่านไม่ได้ = **ปิดพฤติกรรม** (ไม่ใช่เปิด)

**ข) รายการ hook:** **R6-4** อนุมัติ "ในหลักการตามรายการที่ระบุในแผน" แต่ในแผน §2 มีเพียง
- ข้อ 2: patch `StartWorking` (6p = `0x9CABF0` / string = `0x6603F0`) — ระบุชัด
- ข้อ 2 ท้าย: "ตัวขับวันเดิมทุกสาย … ต้อง gate หรือแปลง" — **ไม่ระบุ method** (และยังมี `ฯลฯ` ตามข้อ 2 ของรีวิวนี้)
- ข้อ 8: ปิด skip/เร่งเวลา — ระบุชื่อ `SkipButtonClicked`/`SetSkippingState` + ปุ่มเร่งเวลาเหมือง (ไม่ระบุ method)

⇒ การอนุมัติ "ตามรายการในแผน" จะกลายเป็นการอนุมัติ **ชุดเปิด** ซึ่งขัดหลัก fail-closed ที่ใช้มาตลอด (S2a-4 M5-3 เคยห้าม hook เลยเพราะเหตุนี้)
