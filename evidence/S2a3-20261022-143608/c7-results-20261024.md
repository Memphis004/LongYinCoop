## 2. X4 root cause (measured + code reading — not fixed)

- First B3 run: `gaps=0, duplicates=3` → the old `--inject-gap` **incremented** `expected_seq` (duplicates, no resync).
  Fixed in `tools/viewer-client.py` (inject after ≥4 snapshots, **decrement** expected); rerun B3b: `gaps=1, resync_sent=3, ack=3`.
- Host served resync 3/3 and its own ndjson contains `seq 6/7/8` with **`"resync":true,resyncFromSeq=2`**.
- Guest decoded the same seq 6/7/8 as **`resync:false,resyncFromSeq=0`** ⇒ the flag never reaches the wire.
- Code: `S2/Sender/S2Sender.cs` builds `payload = S2FrameCodec.Encode(frame, hash)` **before** setting
  `frame.Resync = resync` / `frame.ResyncFromSeq` (≈ lines 455–471), so the encoded envelope always carries 0
  while the ndjson line (written later) shows 1. Needs a build/deploy to fix ⇒ not done in this run.

## 3. X5 confound (why the +6.94 ms is not attributable to S2)

- p99 of the same 60 s windows drifts on its own: phase-A windows measured **27.782 / 27.776** but earlier in the same
  game session (S2 off, no client) **34.721**; later phase-B windows **20.839** while W/B were running.
- The 34.7 ms level therefore exists with S2 disabled and no guest; the B1/B2 value equals that level, so the delta
  cannot be assigned to the guest stall/disconnect. Criteria were not changed; verdict stays FAIL on the raw numbers,
  but no causal claim is made. A repeat with more windows (and a longer meter ring) is the next measurement step.
