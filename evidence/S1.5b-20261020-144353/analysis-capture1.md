## 3. stateHash กับ `infoCount` — ข้อมูลจริง

| การวัด | ผล |
|---|---|
| คู่ตัวอย่างติดกัน (in-battle) | 1,944 |
| hash เท่าเดิม | **1,712 (88.1%)** |
| hash เปลี่ยน | 232 (11.9%) |
| longest run ที่ hash เท่าเดิม | **133 ตัวอย่าง** |
| เปลี่ยนเพราะ `infoCount` อย่างเดียว | **33 / 232 (14.2%)** |
| เปลี่ยนโดยไม่เห็นฟิลด์ที่ capture ไว้เปลี่ยนเลย | 63 (per-unit hp/cell เปลี่ยน — hash มีหน่วยทุกตัว) |
| `infoCount` ในศึกนี้ | 22 → 81 (ไม่มี sample ที่ 101) |

**ข้อสรุปเรื่อง `infoCount`:**
1. ในศึกนี้ `infoCount` **ไม่ถึง 101** (จบที่ 81) → ผล S1 ที่ "ค้าง 101" เกิดเฉพาะศึกที่ log ยาวพอ ไม่ใช่ทุกศึก
2. `infoCount` **รีเซ็ตต่อศึก**: ศึกก่อนหน้าจบที่ 101, ศึกนี้เริ่มที่ 22 → ค่าใน hash ไม่ใช่ค่าสะสมข้ามศึก
3. ตอนออกจากศึก status คืน `infoCount=-1` และ `stateHash=null` (ไม่ใช่ hash ของ state ว่าง) → ต้องเช็ค `inBattle` ก่อนใช้ hash
4. **ผลต่อการตรวจ "ไม่เปลี่ยน":** 33 คู่ที่ hash เปลี่ยนเพราะ log line อย่างเดียว พิสูจน์ว่า hash **เปลี่ยนได้แม้เทิร์นไม่ขยับ** → ใน negative test (S1.5-f) การเทียบ hash ก่อน/หลัง 500 ms อาจ FAIL ผิดถ้ามี log line เกิดเองระหว่างนั้น; ต้องอ่าน `infoCount` คู่กันแล้วแยกกรณี หรือเทียบเฉพาะเมื่อ `infoCount` เท่าเดิม (จะบันทึกเป็นข้อจำกัดของ S1.5-f)
5. หลัง `infoCount` ถึง 101 (ศึกยาว) มันจะเป็นค่าคงที่ → ไม่ทำให้ hash เปลี่ยนผิดในช่วงนิ่ง (ทิศที่ negative test เสี่ยง) แต่ก็ไม่ช่วย détect log-only event อีก
